Registro de Operações Multi-Clearing

Ingestão via Kafka, DynamoDB como base de dados única, processamento assíncrono via Streams, SNS e SQS, e exportação analítica via Glue/Athena.

1. Visão geral

O sistema recebe operações de produtos financeiros de duas origens — mensagens Kafka e, no futuro, um arquivo disponibilizado via S3 — e é responsável por registrar cada operação em uma ou mais clearings (B3, SELIC, CIP/Nuclea, com Laqus/CERC/TAG como extensões previstas do mesmo padrão). O DynamoDB é a única base de dados do sistema: fonte da verdade do ciclo de vida de cada operação, sem projeção paralela em banco relacional.

O envio às clearings é orientado a eventos: o DynamoDB Streams dispara o processamento assim que uma operação é gravada, e a resposta da clearing chega de forma assíncrona via SNS, roteada por uma fila SQS antes de atualizar o estado final. Uma exportação noturna via AWS Glue disponibiliza os dados no data mesh da empresa, consultável via Athena, para relatórios e análises que o DynamoDB não atende nativamente.

2. Fluxo de ponta a ponta

Entrada / externo Lambda DynamoDB Mensageria (Streams/SNS/SQS) Reconciliação Analítico (Glue/S3/Athena)

Passo a passo

#EtapaDetalhe
1Kafka → Lambda AA Lambda valida o schema da mensagem por produto e gera o IdExterno — determinístico se a origem puder duplicar a entrega.
2Lambda A → DynamoDBPutItem condicional (attribute_not_exists) garante idempotência na gravação do item OUTBOX.
3DynamoDB Streams → Lambda BDisparo quase imediato após a gravação. Lambda B consulta a tabela de referência para resolver o adapter/protocolo da clearing.
4Lambda B → ClearingEnvio via o protocolo específico (FIX para B3, arquivo/mensageria para SELIC e CIP/Nuclea). Falha de rede não é tratada como sucesso nem rejeição — vai para retry via fila com atraso.
5Clearing → SNS → SQS → Lambda CResposta assíncrona, correlacionada de volta pelo IdExterno ecoado pela clearing. SQS no meio garante buffer, retry e DLQ.
6Lambda C → DynamoDBAtualiza o item OUTBOX (status final) e grava um novo item EVENT#... no histórico — sempre os dois juntos.
7Job de reconciliaçãoRoda periodicamente, lê itens pendentes há mais tempo que o esperado (via GSI) e consulta a clearing diretamente para fechar o estado.
8Glue → S3 → AthenaExportação noturna, separada por tipo de item (outbox_snapshot, eventos_historico, divergencias) para consulta analítica sem sobrecarregar a tabela operacional.

3. Modelagem de dados

O DynamoDB é a única base do sistema, organizada em duas tabelas físicas:

TabelaContémCaracterísticas
OperacoesOutboxTrackingItens OUTBOX, EVENT#... e DIVERGENCIA#..., todos com PK = IdExternoAlto volume, escrita constante, Streams habilitado
ReferenciaClearingMetadados de clearing e mapeamento de status (StatusMapping)Baixo volume, muda raramente, sem Streams

Padrões de acesso

NecessidadeOperação
Gravar operação nova (idempotente)PutItem em SK="OUTBOX" com ConditionExpression: attribute_not_exists(PK)
Consultar status atualGetItem(PK=IdExterno, SK="OUTBOX")
Consultar histórico completoQuery(PK=IdExterno, SK begins_with "EVENT#")
Encontrar pendentes para reconciliaçãoGSI esparsa: PK=StatusEnvio, SK=ProximaTentativa — só itens OUTBOX aparecem
Painel operacional por clearingGSI: PK=ClearingCodigo, SK=StatusEnvio
Traduzir status recebido da clearingQuery em ReferenciaClearing por PK="CLEARING#{codigo}"

5. Decisões-chave e por quê

DynamoDB como única fonte da verdade. Elimina a necessidade de projeção assíncrona entre dois bancos e a complexidade de resolver ordem de eventos entre sistemas distintos.
Lambda em vez de ECS/KCL para consumir o Streams. Nessa escala (milhões de operações/dia), o event source mapping nativo do Lambda entrega throughput suficiente sem gestão manual de shard, sem dependência de JVM/MultiLangDaemon exigida por KCL em ECS.
SNS → SQS → Lambda, não SNS → Lambda direto. A fila no meio garante buffer contra picos, retry configurável e DLQ para respostas de clearing que falhem ao processar.
IdExterno como chave de correlação. Ecoado pela clearing na resposta, é o único jeito da Lambda C saber qual item atualizar quando a notificação chega pelo SNS.
Timeout nunca é sucesso nem falha definitiva. Ausência de resposta dentro do prazo esperado move a operação para um estado explícito de "desconhecido", resolvido pela reconciliação — nunca inferido como confirmado ou rejeitado por omissão.
Exportação para o Glue separada por tipo de item. Um dump bruto da tabela single-table mistura itens OUTBOX, EVENT# e DIVERGENCIA# sob o mesmo schema aparente — a transformação do Glue precisa separar por prefixo de SK antes de escrever no data mesh, senão o Athena fica com um schema impraticável.

6. Pontos em aberto

  • Confirmar que todas as clearings (B3, SELIC, CIP/Nuclea) suportam ecoar de volta o IdExterno na resposta — sem isso a correlação via SNS não funciona.
  • Definir o schema de validação de Atributos por produto na Lambda A, antes da gravação no DynamoDB.
  • Confirmar uso do DynamoDB export-to-S3 nativo como origem do Glue, em vez de Scan direto na tabela, para não competir com a capacidade de leitura operacional.
  • Ingestão via arquivo S3 (segundo canal de entrada) ainda não detalhada neste documento — segue o mesmo padrão da Lambda A, com idempotência determinística por linha do arquivo.
